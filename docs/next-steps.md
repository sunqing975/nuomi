## 1. 架构层：基本合理，三处该收

### 1.1 分层规则基本守住（2 处违规）

现状：`transport(2289行) → domain(2354行) → infra(4858行) → octop-harness`，依赖方向只允许向内。
实测越界**只有 2 处**，且都是"infra 反向依赖 domain"：

| 位置 | 依赖了什么 | 为什么是问题 | 怎么收 |
|---|---|---|---|
| `infra/plugins/market.py:19` | `domain.plugins.service.plugin_service`（取已安装列表） | infra 依赖 domain 的**单例**，等于把领域逻辑焊进了适配层（也埋着循环导入风险） | 把 `installed` 作为参数传进来，由 transport 组装 |
| `infra/memory_store.py:35`（我写的） | `domain.agents.service.agent_workspace_dir` | 同上：**路径解析**被放在 domain，于是 infra 想算个文件路径就得反向依赖 | 把工作区路径解析挪到 `storage/`（或 `config.py`）—— 它本来就只是"数据根 + agent_id 拼接"，不是领域概念 |

**顺带确立一条边界**：*路径解析属于 storage/config，不属于 domain*。收掉这两处之后 `infra` 对 `domain`
的依赖为 0，这条规则就真的能靠 grep 守住了（现在不行，因为存在合法例外）。

### 1.2 `transport/api.py` 是单体：71 个端点 / 1658 行

实测：`api.py` 里 **71 个端点**（29 GET / 24 POST / 8 DELETE / 6 PUT / 4 PATCH），1658 行 ——
是全仓最大的文件（第二名 `domain/avatar/service.py` 602 行）。它同时承担：请求校验、权限、编排、
持久化、SSE 转换、事件广播。

**它已经是维护瓶颈**：本轮改对话链路时，`_TOOL_OWNERS`、`tools()` 急切求值、分页语义、
SSE 心跳、error 帧全都落在这一个文件里；每加一个能力域就再长一截。

**但拆分已经有现成范例**：`transport/memory_api.py`（本轮新增）就是"独立 router + 自带端点"的形态，
挂载方式在 `main.py` 一行。建议按域拆：`agents_api` / `chat_api` / `settings_api` / `plugins_api` /
`skills_api` / `connectors_api` / `knowledge_api`(已有) / `avatar_api` / `memory_api`(已有)。
**分步做，一次拆一个域**，每步跑 `make check` —— 1600 行的一次性重构风险不值得。

### 1.3 同步 SQLite 跑在事件循环上：实测**不是问题，别重构**

这是最容易"看起来该做"的重构。先用数据说话 —— 常驻后端实测（curl 计时）：

| 端点 | 实测 |
|---|---|
| `GET /api/threads` | 1.0 ms |
| `GET /api/connectors` | 1.0 ms |
| `GET /api/skills` | 3.7 ms |
| `GET /api/agents` | 4.3 ms |
| `GET /api/plugins` | 6.1 ms |
| `GET /api/agents/{id}/memory?limit=50`（最慢） | 16.5 ms |

全仓的 sqlite 访问都是同步的（`with db.connect()`，Python `sqlite3` 没有异步驱动），理论上会阻塞
事件循环。但：单用户、本机文件、查询都在 20ms 以内 —— **一次对话要跑几秒，20ms 的阻塞在噪声里**。

**结论：不做异步化改造。** 真出问题的信号是"某条查询 >200ms 且发生在对话热路径上"，
到那时也是先加索引/改查询，而不是引入异步 DB 层。这条写在这里，是为了**下次有人（或 agent）
提议"上 aiosqlite / 数据库连接池"时，先看这组数字**。

### 1.4 一条已知危险应该变成结构性保证

已记录的坑：**`StreamingResponse` 的 generator 里抛 `HTTPException` 不会转成 400**，连接直接中断，
调用方只看到"流断了"。所以 per-turn 参数校验必须在端点函数体、`async def gen()` 之前执行 ——
这条规矩现在只写在 `HANDOVER.md` §6 和 `AGENT.md` 里，**靠人记住**。

本轮已经踩过它的近亲（SSE 里 `aclosing` 的传播机制被写错过两次）。建议做成结构性保证，二选一：
① 一个 `@validate_before_stream` 装饰器/helper，把"校验→再进 gen"这个形状固定下来；
② 一条测试，扫描所有返回 `StreamingResponse` 的端点，断言其函数体内（进 gen 之前）没有可抛
`HTTPException` 的裸调用。**①更实在**，②容易写成假测试。

### 1.5 与 octop-harness 的边界（供参考，暂不动）

分工目前是"harness 出机制、nuomi 写业务"（见 `architecture-refactor-harness.md`），实际守得不错：
`infra/harness/` 是唯一适配层，`stream_octop_sse` 只此一份（无重复实现）。
值得记一笔的是：`infra/memory_store.py` 是**双路径**设计 —— 读直接 SQL 引擎的库、写走引擎 API。
理由充分（引擎没有可视化所需的查询接口），代价是**耦合引擎 schema**：本轮就踩到了
"表名前缀按专家名生成且各不相同"和"引擎初始化后 FTS 触发器让外部连接写不进去"两个坑。
**判断：可接受**（读路径只读、有回归测试锁住），但**升级 octop-memory 时必须重跑记忆测试**。

## 2. 前端界面：定位已经变了，但界面还是按"调试形态"盖的

### 2.1 最重要的判断：控制台就是主界面

`AGENT.md` 明确记着（用户 2026-10-06 拍板）：**壳只订阅对话消息、不做对话入口**，
对话发生在控制台。于是：

- **壳（`shells/nuomi-avatar`）** = 形象层：数字人 + 动作/表情（+未来的语音）
- **控制台（`frontend`，`:8000/console/`）** = **真正的产品界面**：对话、能力管理、记忆

但控制台的历史定位是"**web 控制台只是调试形态**"（2026-10-04 决策）。**这个错位是当前
前端最大的问题**：它是主界面，却按调试工具的标准在建 —— 没有设计系统、没有组件层、
信息架构按"功能罗列"而不是"用户怎么用"。

### 2.2 量化现状（这就是"没有设计系统"的样子）

| 指标 | 实测 | 说明 |
|---|---|---|
| `pages/Chat.tsx` | **983 行** | 主界面 + 最复杂的文件；消息气泡、输入区、能力选择器、滚动、流式全在里面 |
| 内联 `style={{` | **278 处**（Chat 一个文件 78 处） | 每次改样式都在改 JSX |
| `components/` 目录 | **不存在** | 零可复用基元：每个页面自己拼 `Card + List + Empty + Alert` |
| 全局 CSS | 59 行 | 几乎没有共享样式 |
| 裸色值 | 60 处 | token 层已建（`theme.ts` 单一来源），但装饰色板三份重复 |
| 导航项 | 10 个 | 平铺，无分组 |

好消息：**token 层已经建好了**（`theme.ts` 唯一来源 + 启动注入 CSS 变量 + 结构性测试），
所以"颜色"这一层已经不是问题。缺的是**组件层**。

### 2.3 建议：先立组件层，再谈美化

顺序很重要（反着做会返工）：

1. **抽 `src/components/` 基元**：`PageCard`（统一卡片外壳）、`EntityGrid`（各管理页那套等宽等高卡片网格，
   现在 Skillhub/插件/AI 数字人各写一遍）、`EmptyState`、`ErrorState`（含重试）、`SectionToolbar`。
   **先服务 Chat，再回填其他页** —— 不要为了"统一"去重写 8 个页面。
2. **拆 `Chat.tsx`**：`MessageList` / `MessageBubble`（含工具步骤折叠、引用标签）/ `Composer`（输入区 +
   能力选择器 + chips）/ `useChatStream`（把流式状态机抽成 hook，现已 983 行里塞着 abort/done 兜底/
   重试/滚动跟随）。**这步是纯重构，行为不变，靠现有 44 条前端测试兜底**。
3. **然后才是深色主题**：`THEME_OVERRIDES.dark` 已备好，接入 = 换 antd `algorithm` + 一个开关。
   有了基元层，它是一小时的事；没有基元层，它就是"改 278 处内联样式"。

### 2.4 信息架构：10 项平铺，且把核心承诺埋了

现在的导航：对话 / 专家 / 插件 / 技能 / 连接器 / 知识库 / 记忆 / AI 数字人 / 设置 / 存储。

两个问题：
- **"记忆"被埋在能力列表中间** —— 而"**记得你**"是这个产品的核心承诺（本轮刚做完可视化）。
  它不该是一个平级菜单项，而应该是**对话的伴生视图**（聊天里一个侧栏/抽屉："我记住了你什么"），
  让用户在日常对话里自然看到。
- **"设置/存储"这类系统项与"专家/技能"这类能力项混在一起**。建议三分组：
  **对话** ｜ **能力**（专家·技能·技能包·插件·连接器·知识库）｜ **系统**（AI 数字人·设置·存储）。

### 2.5 明确不做（前端）

- ❌ **i18n**：单用户中文形态；且 `frontend/src` 里**没有** i18n 基建（旧文档谎称已做完）。
- ❌ **移动端/响应式重做**：桌面 Electron 形态，200px 侧栏 + 宽表格本来就不面向手机。
- ❌ **换 UI 库 / 上 Tailwind**：antd 5 够用，换库等于重写 18 个页面，收益与风险不成比例。

## 3. 产品发展：核心闭环已通，下一步是"主动性"

### 3.1 现在能做什么（已实测可用）

对话（SSE 流式、可中止、工具步骤可见）· 工具（插件 3 个 + 技能 + 连接器 MCP + 知识库语义检索）·
**记忆**（21 条真实断言 / 10 个实体，可视化 + 可遗忘）· 专家（4 个，独立工作区与记忆）·
数字人形象（VRM 3D、动作/表情由 LLM 主动调用）· 模型（多 Provider、任意 OpenAI 兼容端点 →
**本地模型已天然支持**）· 可观测性（Langfuse 轨迹 + `usage` 帧）

### 3.2 三个真实缺口（按价值排序）

#### ① 主动性 —— 最高价值，且**完全空缺**

**实测：全仓没有任何调度器/定时/主动发起能力**（`scheduler|cron|定时` 命中 0）。
而人设文件 `PROACTIVE.md` / `HEARTBEAT.md` **只被 importer 复制，从未被读取**。

为什么这是第一优先级 —— 人设规则本身就在要求它。`experts/nuomi/AGENTS.md` 写着：

> 「如果他说过的事正合适，就像真的想起来一样带进对话：'你上次说那个 deadline 提前了……后来怎么样了？'」

这句话**没有调度器就永远不会发生**（所有对话都由用户发起）。而"记得你、在乎你"正是产品定位。
所以这不是"加个功能"，是**让已写下的产品承诺真的成立**。

需要什么（v1 最小闭环）：
1. **调度器**：`asyncio` 常驻任务 + 持久化作业表（复用现有 sqlite）；重启后恢复。
2. **主动轮次**：到点后**以糯米自己的身份**发起一轮对话（走现有 chat 管道 + 记忆上下文），
   产出消息挂到某个线程上。
3. **触达面**：控制台里出现未读标记；壳侧弹气泡/播 TTS（可选）。
4. **护栏（关键，否则会变成骚扰）**：频率上限（如每天 ≤2 次）、静默时段、**一键关掉**、
   以及"什么值得主动说"的判定（用记忆里的显式承诺，如 deadline/约定，而不是随机闲聊）。
5. **可观测**：主动消息要能看出"为什么触发"（哪条记忆/哪个作业）。

#### ② 语音闭环 —— 差一个开关的量级

**更正一处认知**（我上一轮把它写成"要从零做 TTS"）：**代码全在** ——

- 壳：`js/tts-client.js` + `js/tts-stream-processor.js` 已 require 并接线（`ttsProcessor` 传入渲染进程，
  `config?.tts?.enabled !== false` 判断）
- 后端：`infra/harness/chat.py:361` 已经在发 `{"type":"tts"}` 帧
- 插件：`plugins/tts`（`main.py` + `config.json`）存在

**但 `plugins.tts.enabled = 0`** —— 链路是断在"没启用/没调通"这一步，不是没写。
所以这是**小时级**的事：启用 → 实测一条回复能否出声 → 修链路问题 → 文档记基线。

**真正的空缺是"听"**：没有任何 STT/语音输入（`transcribe|stt` 在项目代码里命中 0）。
"能说会听"的下半段才是新功能（需要一个 STT adapter：本地 whisper.cpp 或云端 API）。
建议顺序：**先说话（便宜、可见）→ 再听力（贵、但更自然）**。

#### ③ 成本可见 —— 数据已在，没展示

`usage` 帧（`input_tokens`/`output_tokens`）后端一直在发，但前端只有 `Storage.tsx` 沾了一点，
**聊天界面看不到**。对一个每天重度使用的用户，"这一轮花了多少/这个月花了多少"是刚需
（尤其接了多个 Provider 之后）。

便宜的做法的：Chat 每条回复尾部显示 token 数（hover 显示明细）；`Storage` 页加
"按天/按模型汇总"。数据源现成，纯展示工作。

### 3.3 更远的方向（含取舍，先别做）

| 方向 | 价值 | 取舍/前置 |
|---|---|---|
| **专家协作（糯米找专家帮忙）** | 高：harness 有 subagent 机制，"多专家"叙事才成立 | 需要先想清楚"谁决定委派、结果怎么合并"，否则只是把一次对话变慢 |
| **定时提醒**（"明天 9 点提醒我"） | 高：主动性的具体形态，用户可感知 | 与 ① 共用调度器 —— ① 做出来后这是自然延伸 |
| **记忆纠正 UI 增强** | 中：现在能"遗忘"和手改文件 | 更自然的是在对话里说"不对，是 X"→ 模型改写记忆（依赖引擎的更新语义） |
| **知识库 OCR** | 中：扫描 PDF 现在被门禁挡 400 | 方案已有（`knowledge-base-research.md` §8），RapidOCR 本地 |
| **会话导出/分享** | 低：单用户 | 只在"想留档/给别人看"时才有价值 |
| **手机/远程访问** | 低 | **与"住在你电脑里"的定位和本机安全模型冲突**（守卫假定只允许本机） |
| **插件沙箱** | 低 | 单用户、插件自己的作者就是用户，沙箱化成本极高收益极低 |

## 5. 明确不做（附理由，别再排）

| 事项 | 理由 |
|---|---|
